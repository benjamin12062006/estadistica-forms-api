# Estrategia de Entornos y Bases de Datos (Desarrollo, Pruebas y Producción)

Sí: no deberías desarrollar diariamente contra la base de producción.

Para este proyecto, la opción óptima es utilizar un enfoque híbrido por entornos:

1. **SQLite / libSQL local** → Desarrollo rápido y pruebas manuales sin dependencia de red.
2. **Turso remoto de desarrollo** → Comprobar la conexión real con Turso / Vercel en entornos de prueba o _Preview_.
3. **Turso remoto de producción** → Datos reales de usuarios finales.

---

## Situación Actual y Limitaciones

Lo que ya tienes configurado:

```bash
pnpm db:verify
```

Usa actualmente una base temporal en memoria. Sirve para probar rápidamente que las migraciones corren correctamente, pero **desaparece al terminar** la ejecución; por tanto, no sustituye una base de datos local persistente.

Actualmente, tu `TursoService` acepta únicamente una URL remota del tipo:

```txt
libsql://...
```

y exige un token de autenticación (`TURSO_AUTH_TOKEN`). Debido a esto, todavía no puede abrir una base de datos local mediante un descriptor como:

```txt
file:./.data/estadistica-dev.db
```

Sin embargo, el paquete `@libsql/client` que ya utilizas en el proyecto **sí soporta bases de datos locales con el prefijo `file:`**. Será necesario adaptar el servicio y el script de migraciones para aceptar ambos modos de conexión de manera flexible.

## Recomendación Concreta de Entornos

### 1. Tu Ordenador (Desarrollo Local)

- **Ruta de la Base de Datos:** `.data/estadistica-dev.db`
- **Uso:** Datos de prueba y experimentación. Puedes borrarla y recrearla en cualquier momento sin miedo.

### 2. Turso Development (Remoto de Pruebas)

- **Base de datos:** `estadistica-forms-dev`
- **Uso:** Pruebas reales de conexión remota, despliegues _Preview_ y validaciones integradas antes de pasar a producción.

### 3. Turso Production (Remoto de Producción)

- **Base de datos:** `estadistica-forms-prod`
- **Uso:** Almacenamiento de usuarios y datos reales; **nunca** se utiliza para experimentar o realizar pruebas destructivas.

## Flujo de Migraciones

La misma migración SQL se aplica de forma idéntica en cada base de datos:

```text
migrations/001_create_app_users.sql
                 │
                 ├─► Local dev DB       → pnpm db:migrate
                 ├─► Turso dev DB       → pnpm db:migrate
                 └─► Turso prod DB      → pnpm db:migrate
```

> **Nota:** Cada base de datos gestiona su propia tabla interna `schema_migrations`, por lo que cada entorno mantiene un registro independiente y autónomo de qué cambios ya han sido aplicados.

## ¿SQLite Local o Turso? (Ventajas de usar ambos)

Como Turso / libSQL está basado en arquitectura SQLite, una base de datos local es altamente compatible y ofrece enormes ventajas para el desarrollo diario:

### Ventajas de SQLite Local (`file:./.data/estadistica-dev.db`)

- No dependes de conexión a Internet.
- Puedes reiniciar, corromper o borrar los datos sin poner en riesgo nada.
- Velocidad de lectura/escritura inmediata.
- Aislamiento total frente a datos remotos o usuarios reales.

### ¿Por qué sigues necesitando Turso Remoto?

Una base local no reemplaza por completo a Turso en la nube, ya que en remoto también intervienen factores críticos:

- Credenciales (`DATABASE_URL` y `TURSO_AUTH_TOKEN`).
- Latencia y comportamiento de conexión por red.
- Configuración de variables en Vercel.
- Permisos de acceso y restricciones de seguridad.
- Comportamiento real del servicio desplegado.

Por este motivo, el flujo recomendado es:

1. **Código diario / Pruebas:** Base de datos local.
2. **Validación previa al despliegue:** Turso Development.
3. **Paso a producción:** Turso Production.

## Cómo Publicar Cambios sin Romper el Sistema

Evita cambios destructivos o dependientes de un solo despliegue masivo. El patrón recomendado consiste en **migraciones compatibles (expandir y contraer)** y despliegues graduales.

### Ejemplo práctico: Añadir una foto de perfil (`avatar_url`)

- **Paso 1 — Ampliar (sin romper):**

  ```sql
  ALTER TABLE app_users ADD COLUMN avatar_url TEXT;
  ```

  _(La nueva columna permite valores `NULL`, garantizando que el código anterior que aún no la usa siga funcionando sin errores)._

- **Paso 2 — Desplegar código compatible:**
  Se despliega el nuevo backend, el cual está preparado para manejar tanto usuarios con `avatar_url` como aquellos donde este campo es nulo.

- **Paso 3 — Activar la funcionalidad de forma gradual:**
  Puedes emplear un mecanismo de _feature flags_:
  1. Primero tú (entorno de pruebas).
  2. Luego usuarios internos o de alfa.
  3. Un porcentaje reducido de usuarios (ej. 10%).
  4. Liberación general al 100%.

- **Paso 4 — Limpieza posterior:**
  Únicamente cuando ningún código antiguo dependa de estados previos, se realizan migraciones de endurecimiento si fuese necesario.

Este patrón se resume en la secuencia:

> **Expandir ➔ Desplegar compatible ➔ Migrar datos ➔ Activar ➔ Limpiar**

Así, una migración de base de datos no rompe la aplicación ni obliga a cambios abruptos.

## Siguientes Mejoras Recomendadas

Como siguiente paso práctico, se sugiere implementar las siguientes configuraciones:

1. **Ignorar la base local en Git:**
   Añadir `.data/estadistica-dev.db` (o toda la carpeta `.data/`) al archivo `.gitignore`.

2. **Soportar entorno dual en las variables de entorno (`.env`):**
   Permitir alternar entre archivo local o conexión remota mediante la configuración:

   ```env
   # Para desarrollo local con SQLite persistente:
   DATABASE_URL=file:./.data/estadistica-dev.db

   # O bien para Turso remoto:
   # DATABASE_URL=libsql://tu-base-dev.turso.io
   # TURSO_AUTH_TOKEN=tu-token-aqui
   ```

3. **Consistencia:**
   Mantener exactamente la misma carpeta `migrations/` para todos los entornos.

La idea central es clara: **la estructura del esquema SQL es exactamente la misma en todas partes; lo único que cambia según el entorno son la URL de conexión, el token de acceso y los datos almacenados.**
